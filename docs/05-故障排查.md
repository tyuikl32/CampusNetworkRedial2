# 故障排查
面向**已部署完成、运行中出问题**的现场：按现象找原因、按原因给修法。每节统一四段 —— **现象** / **快速定位**（可粘贴命令 + 判据）/ **根因** / **修法 / 回滚**。
实测数字全部来自 Redmi AX3000（`ipq50xx/arm`，QSDK 11.5.0.5，内核 `5.4.164`，社区 OpenWrt 21.02.7，fw3+iptables，BRAS 华为 ME60-X8A）。命令块前 `# [路由器]` / `# [Windows]` / `# [WSL]` 表示执行机器。全文无真实凭据，一律 `<校园网账号>` / `<PPPoE口令>` / `<路由器SSH口令>`。

## 1. 拨号 / 认证类

### 1.1 CHAP `E2553: Password is error` —— `pppoe-wan` 起不来，`logread` 反复出现 `Remote message: E2553: Password is error`。
**快速定位**：
```sh
# [路由器] 看 BRAS 原话，不要只看"拨号失败"；口令只输出长度，不打印明文
logread | grep -Ei 'E25[0-9]{2}|pppd|CHAP' | tail -20
uci get network.wan.password | wc -c
```
判据：`E2553` 是**口令本身不对**（不是账号），与 `E2531`（账号）严格区分。
**根因**：实测踩过两次，都是**把别的口令填进了 PPPoE 口令字段** —— 最典型的是把**路由器的 SSH 口令**误当 PPPoE 口令写进 `network.wan.password`，于是 `pppd` 反复用错口令做 CHAP。
**修法 / 回滚**：
```sh
# [路由器] 回滚：cp /etc/config/network.campus-redial.bak /etc/config/network && ifup wan
uci set network.wan.username='<校园网账号>'; uci set network.wan.password='<PPPoE口令>'
uci commit network; ifup wan; ip -4 addr show pppoe-wan    # 判据：有 inet 地址
```
注意账号池凭据是分开存的（`campus-redial.main.pppoe_username/pppoe_password` 与 `campus-redial.<N>.username/password`），只改一处会出现「主 WAN 通了、池子全失败」。

### 1.2 CHAP `E2531: User not found` —— `logread` 出现 `E2531: User not found`，而账号「看起来是对的」。
**快速定位**：
```sh
# [路由器] 查尾空格要看长度，不要看内容
uci get campus-redial.1.username | wc -c              # 期望 = 账号字符数 + 1（仅结尾 \n）
uci get campus-redial.1.username | od -c | tail -3    # 期望结尾是 \n，不是空格后跟 \n
```
判据：`wc -c` 比预期多 ⇒ 有尾部空白；`<账号> ` 与 `<账号>` 在 BRAS 眼里是**两个账号**。
**根因**：账号池条目 `campus-redial.<N>.username` 带了尾空格（人工填写/复制粘贴带入），BRAS 按字面串查用户 ⇒ `E2531`。
**修法 / 回滚**：
```sh
# [路由器] 用 tr 剥掉全部空白后写回
uci set campus-redial.1.username="$(uci get campus-redial.1.username | tr -d '[:space:]')"
uci commit campus-redial; /etc/init.d/campus-redial restart
```

### 1.3 CHAP `E2532: ... interval cannot be less than 3 seconds` —— 连续重拨/多拨时 BRAS 回 `E2532: The two authentication interval cannot be less than 3 seconds`。
**快速定位**：
```sh
# [路由器] 看相邻两次认证的间隔；last_auth 是守护进程自己记的时间戳
cat /var/run/campus-redial/last_auth; grep -Ei 'E2532' /var/log/campus-redial.log | tail -10
```
判据：出现 `E2532` ⇒ 距上次认证 < 3 秒。这是 **BRAS 侧**限制，与本地 `auth_interval_seconds` 是两回事。
**根因**：ME60-X8A 对同一账号的两次认证强制 ≥ 3 秒间隔；本地节流（`auth_wait` + `/var/run/campus-redial/last_auth`）一旦被调小或被绕过就会撞上。
**修法 / 回滚**：
```sh
# [路由器] 认证间隔不得低于 BRAS 下限；多拨场景用 60 s（已验证 5/5 成功）
uci set campus-redial.main.auth_interval_seconds='60'; uci commit campus-redial
/etc/init.d/campus-redial restart
```

### 1.4 同 MAC 多会话被 BRAS 发 `PADT` 踢掉 —— 想不建 macvlan、直接用同一个 MAC 起第二条 PPPoE，结果第二条一起来**连原主会话一起被踢**，`logread` 里能抓到 `PADT`。
**快速定位**：
```sh
# [路由器] 一条通道手工起第二条同 MAC 会话（会打断 WAN，做完必须恢复）
pppd nodetach nodefaultroute noauth maxfail 1 ifname crtest-ppp \
     user '<校园网账号>' password '<PPPoE口令>' plugin rp-pppoe.so nic-eth0
# [路由器] 另一条通道同时盯 PADT；判据：出现 PADT ⇒ 同 MAC 多会话被拒，且连原会话一起踢
logread -f | grep -i padt
```
**根因**：BRAS 华为 ME60-X8A **禁止同 MAC 多会话** —— 这正是本项目必须靠 macvlan 拿独立 MAC 的意义。
**修法 / 回滚**：此路线**不可行，不要再用**。恢复被打断的主会话，改走 macvlan 路线（§2.4/§2.5）：
```sh
# [路由器] 期望：pppoe-wan 有 inet + 默认路由；crwan2 是独立 MAC 的 macvlan 从设备
ifup wan; ip -4 addr show pppoe-wan && ip route | grep '^default'; ip link show crwan2
```

### 1.5 VLAN 多拨：PADI 发得出去、`PADO` 永远超时 —— 用 `wan.3` 之类 802.1Q 子接口拨号，抓包看 PADI 出去了（源 MAC 已换新），但收不到 PADO，拨号永久超时。
**快速定位**：
```sh
# [路由器] 确认有无残留 VLAN 子接口在充当多拨下层设备（应该没有）；需要看链路层时抓一下（只读）
ip -d link show | grep -A1 -i vlan ; lsmod | grep 8021q
tcpdump -i eth0 -n -c 20 'ether proto 0x8863 or ether proto 0x8864'
```
判据：PADI 有、PADO 无 ⇒ 上游丢了带标签帧，不是本机问题。
**根因**：内核 `vlan_dev_hard_start_xmit()` **对 VLAN id 0 也照样插 4 字节 802.1Q 头**（TCI=0 优先级标签）。实测 id 0 的 PADI 确实用新 MAC 发出但**无 PADO**，OLT/BRAS 丢弃带标签帧。所以「同 MAC 靠 VLAN 隔离」「id 0 拿独立 MAC」两条路都被否。
**修法 / 回滚**：改用 `macvlan`（本项目已切换，依赖从 `kmod-8021q` 换成 `kmod-macvlan`）。清残留：
```sh
# [路由器]
ip link del wan.3 2>/dev/null; ip link del v0 2>/dev/null; ifup wan && ip -4 addr show pppoe-wan
```

## 2. 多拨连接池类

### 2.1 mwan3 判 `wan2/wan3 is error (16)`，完全不分流 —— `mwan3 status` 出现 `interface wan2 is error (16) and tracking is active`，`cr_balanced` 里三条都列了（各 33%）但实际只用 `wan`；12 条并发下载全走 `pppoe-wan`（`+59.7 MB`），`wan2/wan3` 增量 **0**。
**快速定位**：
```sh
# [路由器] 1) 关键是看 mwan3 每接口表里有没有 default（(16) 的真正含义）
ip route list table 5 ; ip route list table 6
#   坏：只有 10.194.255.254 dev pppoe-wan2 proto kernel scope link src … + 192.168.6.0/24
#   好：多一条 default via 10.194.255.254 dev pppoe-wan2
ip route list table main | grep '^default'
#   坏：只有 default via 10.194.255.254 dev pppoe-wan proto static
# [路由器] 2) 对照 tracker 的真实状态（它其实说 online）：error (16) 与真实跟踪状态不一致
cat /var/run/mwan3/iface_state/wan2 2>/dev/null ; mwan3 status | grep -E 'wan2|wan3'
```
判据：**每接口表里没有 `default`** ⇒ 命中 `error (16)`。
**根因**（已定位到源码级，与 macvlan 无关）
1. `mwan3_report_iface_status()`（`/lib/mwan3/mwan3.sh:1027+`）用**位掩码**自检，`+16` 这一位就是 `[ -n "$(ip route list table $id default dev $device)" ]` 失败。
2. mwan3 的每接口路由表由 `mwan3_create_iface_route()` 建立，源是 `mwan3_get_routes()` = **`ip route list table main`**（外加 `globals.rt_table_lookup`）。
3. **netifd 只为「主」PPPoE 装默认路由** —— main 表里只有 `pppoe-wan` 那条；`wan2/wan3` 的默认路由**从未进 main**（`ifstatus wan2` 里有 `route[0]` 模型，但没落到 main）。
4. ⇒ mwan3 没东西可拷进表 5/6 ⇒ 表里只剩对端链路路由 ⇒ `error=16` ⇒ 该接口被排除出策略。
5. `mwan3 ifup wan2` / `mwan3 restart` **都救不了**（`RTNETLINK answers: File exists`；重启后重建路由同样没有源）。
**修法 / 回滚**：临时修法**已验证有效但非持久**（接口一 bounce 就没了）；持久化两案**尚未在实机定案**（见 §6）。
```sh
# [路由器] 临时：判据是 wan2/wan3 变 online，且分流实测 wan=+11.56 / wan2=+20.71 / wan3=+15.23 MB
ip route add default via 10.194.255.254 dev pppoe-wan2 table 5
ip route add default via 10.194.255.254 dev pppoe-wan3 table 6
mwan3 status
# [路由器] 持久化方案 A（推荐）：让 netifd 把该接口默认路由直接装进 mwan3 那张表。
#   mwan3 的 id 按配置顺序分配（wan=1,wan6=2,wanb=3,wanb6=4,wan2=5,wan3=6 ⇒ 表 5/6），
#   删掉出厂 section 表号会漂 ⇒ 应由 ensure_mac_session 反查而不是写死
uci set network.wan2.ip4table='5'; uci set network.wan3.ip4table='6'; uci commit network
# [路由器] 持久化方案 B：让默认路由进 main，再由 mwan3 拷进每接口表
uci set network.wan2.defaultroute='1'; uci set network.wan3.defaultroute='1'; uci commit network
# [路由器] 回滚（备份目录名以设备上实际为准）
cp /etc/config/.campus-redial-backup-20260911-010140/network /etc/config/network
ip route del default dev pppoe-wan2 table 5 2>/dev/null; ip route del default dev pppoe-wan3 table 6 2>/dev/null
```

### 2.2 路由器自己测速恒为 `0.00 Mbps`，池子无限重拨 —— 三路会话全拨通、各有独立 IP，但 `verified_count=0`、`state=redialing`，日志每路一行 `高宽测速完成：0.00 Mbps（阈值 0，3s 窗口）`，**每 ~30 秒轮着重拨一条**。
**快速定位**：
```sh
# [路由器] 1) 确认是"全 0"而不是"某一路 0"
cat /var/run/campus-redial/status.json ; grep -c '0\.00 Mbps' /var/log/campus-redial.log
# [路由器] 2) 复现时序缺陷（仓库脚本）
sh CampusRedialWrt/kmod-build/remote/cr-diag-speed.sh
```
判据（`cr-diag-speed.sh` 实测对照）：
| 组合 | 结果 |
| --- | --- |
| `--max-time 3` + `sleep 3` + `kill` | **6 路全 0**（撞在同一时刻，kill 赢） |
| `--max-time 2` + `sleep 3` + `kill` | **6 路全有数**，13.8 MB / 2 s ≈ 55 Mbps |
| 手工 `curl --interface <IP>` 单跑 | 60+ MB / 8 s ≈ 62 Mbps |
**根因**（`run_speed_test_session` 的 curl 回落分支）
```sh
( curl -sS -4 --interface "$src" --max-time "$((SPEED_SECONDS+5))" \
        -o /dev/null -w '%{size_download}' "$url" ) > "$RUN_DIR/speed.$name.$stream.count" &
sleep "$SPEED_SECONDS"; for pid in $pids; do kill "$pid"; done
for pid in $pids; do wait "$pid"; done     # 紧接着就读 count 文件
**BusyBox ash 会把 `( 单命令 ) &` 优化成 exec**，于是 `$!` 就是 curl 本身；curl 只在**自己退出时**才打印 `%{size_download}`，而它的 `--max-time` 是 `SPEED_SECONDS+5` —— `kill` 比它早 5 秒，**curl 每次都在报数前被杀** ⇒ 恒 0。前提：设备上**没有 `campus-redial-bind.so`**（全盘 `find` 无命中），必然走 curl 回落分支；`uclient-fetch | wc -c` 分支**同病**。

# [路由器] 注意 enabled=1 时重启后守护进程会自动起池，churn 会自己回来
uci set campus-redial.main.mbps200_enabled='0'    # 关掉测速模式
uci set campus-redial.main.enabled='0'            # 或整体停用
uci commit campus-redial; /etc/init.d/campus-redial restart
```

> **探针判定规则（2026-09-11 统一口径，PC 侧 C#／PowerShell 与路由器守护进程必须一致）**：
> **只要收到了 HTTP 响应就算"打通"** —— `200/302/404/500` 一律算成功；**只有超时、连不上、
> DNS/TLS 失败才算失败**（那才是"没探到好出口"，应当继续重拨）。探针测的是"这个出口能不能把
> 请求送到目标"，不是"目标页面是否存在"。
>
> 两个取数后端对"非 2xx"的语义**不一样**，这正是最容易被写错的地方（已修，见 §2.2 相关提交）：
>
> | 后端 | 404 时的行为 | 处理 |
> | --- | --- | --- |
> | `curl` | 退出码 **0**（默认不为状态码报错） | 直接用退出码即可；另用 `-w '%{http_code}'` 兜住"先收到响应、随后连接卡住"的情况 |
> | `uclient-fetch` | 退出码 **8**（wget 语义：server issued an error response） | **必须把 8 归一化成成功**，否则 canary 一返回 404 就会被判成坏出口 ⇒ 池子无限重拨 |
> | `uclient-fetch` 的额外坑 | **会跟随重定向**，且没有关掉的开关 | "302 之后跟到被墙的下一跳"与"根本没连上"退出码相同，失败时用 `curl` 复核一次状态码来区分 |
>
> 自查命令（现场跑，两套后端各 5 个用例，期望 `FAIL=0`）：
> ```sh
> # [路由器]
> sh CampusRedialWrt/kmod-build/remote/cr-probe-rule-test.sh        # 默认取 pppoe-wan 接口
> ```
> 注意：池子正在重拨时 PPPoE 源地址会抖动，脚本会把这类用例标成 `SKIP(iface down)` 而不是 `FAIL`。

### 2.3 池子无限重拨导致主 WAN 公网 IP 频繁变化 —— 用户正在用的连接被打断，`pppoe-wan` 公网 IP 一天内多次变化（实测 `10.194.238.20` → `10.194.169.28`）。
**快速定位**：
```sh
# [路由器] 判断是重拨 churn 还是 BRAS 断线；state 长期 redialing + 每 ~30 s 一轮 = churn
grep -cE '重拨|redial' /var/log/campus-redial.log; cat /var/run/campus-redial/status.json
grep -E '高宽测速完成' /var/log/campus-redial.log | tail -20
```
**根因**：测速恒 0（§2.2）⇒ `verified_count=0` ⇒ 维护循环判会话不合格 ⇒ 轮着重拨，不是链路问题。
**修法 / 回滚**：见 §2.2 的两条止损命令，回滚方式相同。

### 2.4 日志报「内核未提供 macvlan」 —— 池子只有主会话在线，日志出现明确报错 `内核未提供 macvlan；连接池需要安装匹配的 kmod-macvlan`。
**快速定位**：
```sh
# [路由器]
lsmod | grep macvlan                          # 坏：无输出
ls /lib/modules/5.4.164/macvlan.ko            # 坏：不存在
modprobe macvlan; echo "rc=$?"                # 坏：rc=255
cat /etc/modules.d/30-macvlan 2>/dev/null     # 开机加载清单里应有 macvlan
```
判据：`modprobe macvlan` 非 0 ⇒ 守护进程走「明确报错」分支，**不会**误以为模块可用再去建接口把内核打崩 —— 这是刻意设计的安全行为，不要绕过。
**根因**：设备是 QSDK 自编固件，官方 21.02.7 **没有 ipq50xx target**、core feed 404，kmod 无法从官方源补装；借别的 target 会撞 `PLT section(s) missing` 或 vermagic 不匹配（§4.2）⇒ 只能**用厂商 QSDK 源码自编**（见 `docs/reference/AX3000-KMOD-BUILD.md` §6）。
**修法 / 回滚**：
```sh
# [路由器] 只加载（内存态，重启失效）
insmod /tmp/macvlan.ko; lsmod | grep macvlan
# [路由器] 持久化（写 flash/overlay）
cp macvlan.ko /lib/modules/5.4.164/; printf 'macvlan\n' > /etc/modules.d/30-macvlan
modprobe macvlan && lsmod | grep macvlan
# [路由器] 回滚：期望 modprobe 变成 255（明确失败，而不是带病可用）
rm -f /lib/modules/5.4.164/macvlan.ko /etc/modules.d/30-macvlan; rmmod macvlan
modprobe macvlan; echo "rc=$?"
```
`xt_statistic.ko`（mwan3 加权分流要用）流程完全相同，见 `docs/reference/AX3000-KMOD-BUILD.md` §6.6。

### 2.5 macvlan 不能建在桥端口上（`-EBUSY`） —— `ip link add link eth1 name crtest type macvlan mode bridge` 报 `RTNETLINK answers: Resource busy`（RC=2）。
**快速定位**：
```sh
# [路由器] 先判断目标是桥设备还是桥端口：桥设备 br-lan；桥端口 eth1 / wlan0 / wlan1
brctl show 2>/dev/null || bridge link show
```
判据：目标是**桥端口** ⇒ 必然 `-EBUSY`；是**桥设备本身或独立物理口** ⇒ 可以建。
**根因**：`macvlan_port_create()` 要求 `dev->type == ARPHRD_ETHER` 且 `!netdev_is_rx_handler_busy(dev)`；桥端口的 rx_handler 已被 `br_handle_frame` 占用 ⇒ `-EBUSY`。这是**干净失败**，不崩内核。
**修法 / 回滚**：正式目标是在 **WAN 口 `eth0`** 上建 macvlan，`eth0` 既非桥设备也非桥端口，**不受此限制**；只在自测时才需要换地方，可建在**桥设备本身**：
```sh
# [路由器] 正例（验证用，用完即删）；BusyBox 的 ip 不支持 add 时带 address，必须分两步
ip link add link br-lan name crtest type macvlan mode bridge
ip link set crtest address 02:aa:bb:cc:dd:01 ; ip link set crtest up
ip -s link show crtest        # 判据：TX/RX 计数有变化 = 数据路径真的走通
ip link del crtest            # 回滚
```

## 3. SNI 分流类（zapret：tpws / nfqws）

### 3.1 `/etc/init.d/zapret stop` 造成的全网 connection refused 黑洞 —— 点「SNI 分流 → 停止」（或手工 `stop`）后，面板打不开（超时/连接被拒）；通过路由器上网的**所有** http/https 一律 connection refused；观感与「路由器死机」一模一样，极易误判为 kernel panic。
**快速定位**：
```sh
# [路由器] 1) 先排掉内核问题：stop 前后 dmesg/kmsg 无新增 ⇒ 不是 panic
dmesg | tail -20 ; cat /proc/sys/kernel/tainted        # 期望 0
# [路由器] 2) 关键判据：SSH(22) 通、只有 80/443 挂；跳转还在但进程没了
iptables -t nat -S | grep -cF -- '--to-destination 127.0.0.127:988'   # 坏：2（或更多）
pidof tpws; pidof nfqws                                                # 坏：空
ubus call campus_redial zapret_status                                  # 坏：running=false 但 redirect=true
```
判据：**`!running && redirect`** 就是本故障的形态（进程没了、跳转还在）。
**根因**
1. tpws 模式靠 fw3 include（`/etc/firewall.zapret` → `zapret_apply_firewall`）装两条 DNAT：`-A PREROUTING -i br-lan -p tcp -m multiport --dports 80,443 … -j DNAT --to 127.0.0.127:988` 与 `-A OUTPUT -o pppoe-wan … --dports 80,443 … -j DNAT --to 127.0.0.127:988`。
2. `MODE_FILTER=hostlist` + tpws 的设计是：**iptables 把全部 80/443 都转给 tpws**，由 tpws 自己按 `--hostlist=` 决定给谁分片 ⇒ 跳转覆盖**全部** 80/443，不是只有名单内域名。
3. 旧 `zapret_service('stop')` 只跑 `/etc/init.d/zapret stop`；`INIT_APPLY_FW` 未设置 ⇒ `stop_service()` **不碰防火墙** ⇒ 跳转留在原地。
4. LAN 侧每个 80/443 被 DNAT 到 `127.0.0.127:988`，无人监听 → TCP RST → connection refused。
5. **LuCI 面板自己也在 80 端口**（`-i br-lan` 同样命中）⇒ 管理页一起失联；`OUTPUT` 那条还让路由器自身无法发起 80/443。
**修法 / 回滚**：顺序不能反（先摘跳转、再停进程），`start_fw` 幂等（跳转恢复为精确 2 条）。
```sh
# [路由器] 现场恢复
touch /var/run/zapret.off        # ① 打标记：让 fw3 重载不再把跳转补回来
/etc/init.d/zapret stop_fw       # ② 摘掉 nat 跳转 ← 网络在这一刻恢复直连
/etc/init.d/zapret stop          # ③ 停 tpws
iptables -t nat -S | grep -cF -- '--to-destination 127.0.0.127:988'   # 判据 0
pidof tpws                                                            # 判据 空
# [路由器] 重新开启（顺序相反）
rm -f /var/run/zapret.off; /etc/init.d/zapret start; /etc/init.d/zapret start_fw
```
语义是**仅运行时停止** —— `/var/run` 是 tmpfs，**重启后自动恢复开启**（`/etc/rc.d/S21zapret` 仍在）；要**永久**关需处理 `/etc/rc.d/S21zapret`（写 flash，先确认）。已内置的防复发：rpcd 的 `zapret_apply_action('stop')` 已按上述顺序执行，整条序列用 `( cmd ) >/dev/null 2>&1 &` 后台跑（init 脚本 fork + 动 iptables/ipset 约 1~3 s，同步执行会把 uhttpd 的 chunked 响应掐断）；`/etc/firewall.zapret` 改为**带两层守卫**的版本（守卫 1：`/var/run/zapret.off` 存在或 `/etc/rc.d/S*zapret` 不存在时不装跳转；守卫 2：把访问**路由器自身 IP** 的 80/443 用一条 `RETURN` 摘出来 ⇒ tpws 崩溃/OOM 时**面板仍可达**）；`status` 新增 `redirect`/`off` 字段供前端显示「异常：跳转残留」。

### 3.2 切换/停止后遗留的 `DNAT --to 127.0.0.127:988` 死规则 —— 已切到 nfqws（或已停用分流），`988` 跳转计数却不是 0，例如 `-A OUTPUT -o pppoe-wan5 -p tcp -m multiport --dports 80,443 -j DNAT --to-destination 127.0.0.127:988`。危害：nfqws 模式下 tpws 已不在，**只要 wan5 重新上线**，路由器本机经 wan5 的 80/443 就被投进死端口。
**快速定位**：
```sh
# [路由器] 无条件扫全表，不要按设备名逐条摘：判据是必须为空 / 计数 0
iptables -t nat -S | grep -F -- '--to-destination 127.0.0.127:988'
iptables -t nat -S | grep -cF '127.0.0.127'
```
判据：只要有一条命中就是本故障 —— **不管那条规则引用的设备当前在不在**。
**根因**：zapret 摘规则时**只枚举当前存在的 WAN 设备**。实测切换那一刻 `wan5` 是 down 的（池子当时只有 wan/wan2/wan3/wan4），于是 `-o pppoe-wan5` 那条摘不掉、被静默留下。教训：**「按设备名逐条摘」对「当时不存在」的设备一定会漏。**
**修法 / 回滚**：
```sh
# [路由器] 手工补扫：先看，再把每条 -A 原样换成 -D 执行
iptables -t nat -S | grep -F -- '--to-destination 127.0.0.127:988'
iptables -t nat -D OUTPUT -o pppoe-wan5 -p tcp -m multiport --dports 80,443 -j DNAT --to-destination 127.0.0.127:988
iptables -t nat -S | grep -cF '127.0.0.127'    # 判据 0
# [路由器] 仓库脚本已内置无条件补扫 sweep_tpws_rules；off = stop_everything_safely = stop_fw + 补扫
sh CampusRedialWrt/kmod-build/remote/cr-nfq-switch.sh off
sh CampusRedialWrt/kmod-build/remote/cr-nfq-switch.sh status
# 回滚：on 回到 nfqws；或恢复 tpws 配置（见下）
cp /opt/zapret/config.tpws.bak /opt/zapret/config
/etc/init.d/zapret stop_fw; /etc/init.d/zapret restart; /etc/init.d/zapret start_fw
```

### 3.3 `route_localnet` 未开：DNAT 计数在涨但吞吐为 0 —— 规则明明命中（`iptables -t nat -L PREROUTING -v -n` 计数在涨），但被测路径**吞吐恒为 0**。
**快速定位**：
```sh
# [路由器] zapret 只给 br-lan 打开这个开关；测试网关走别的接口就必须自己开
sysctl net.ipv4.conf.br-lan.route_localnet              # 期望 1
sysctl net.ipv4.conf.<测试网关所在接口>.route_localnet   # 坏：0
iptables -t nat -L PREROUTING -v -n | grep 988          # 佐证：计数在涨
```
判据：**DNAT 计数上升 + 吞吐 0** ⇒ 包在 DNAT 之后被判 martian 丢弃。
**根因**：DNAT 到 `127.0.0.127` 后回程要按本地地址处理；`route_localnet` 未开的接口上该包被当 martian 丢掉。
**修法 / 回滚**：
```sh
# [路由器]
sysctl -w net.ipv4.conf.<dev>.route_localnet=1     # 运行时，重启失效
sysctl -w net.ipv4.conf.<dev>.route_localnet=0     # 回滚
```
测试装置自身用 `CampusRedialWrt/kmod-build/remote/cr-fwd-client.sh` 的清理路径拆除。

### 3.4 面板状态与真实进程不一致（`pgrep -f` 自我匹配） —— tpws 已停，`ubus call campus_redial zapret_status` 仍返回 `"running": true`；面板永远显示「运行中」，启动/停止按钮判断错位。
**快速定位**：
```sh
# [路由器] 对照三方口径：pidof 为空而 pgrep -f 有输出 ⇒ 命中自我匹配
pidof tpws; pidof nfqws ; pgrep -f 'tpws|nfqws' ; ubus call campus_redial zapret_status
**根因**：`luci.sys.exec` 经由 `/bin/sh -c "<cmd>"` 执行，那条 shell **自己的命令行里就含 "tpws"**，`pgrep -f` 匹配到自己 ⇒ 无论 tpws 在不在都报「在运行」。

local out = sys.exec("pidof tpws 2>/dev/null; pidof nfqws 2>/dev/null")
return out ~= nil and out:match("%d") ~= nil
```
> 复用提示：OpenWrt/LuCI 里判断「某进程是否在跑」，**不要用 `pgrep -f <模式>`**，用 `pidof <name>` 或 `pgrep -x <name>`。

### 3.5 hostlist 为空 ≠ 未生效 —— 设备上 `zapret-hosts-user.txt` 是 0 字节，怀疑分流根本没生效。
**快速定位**：
```sh
# [路由器] 空名单：profile 标注 (empty)，没有任何 hostlist check 就直接匹配
wc -c /opt/zapret/ipset/zapret-hosts-user.txt ; logread | grep -i zapret | tail -20
# 写了名单才会出现：hostlist check for www.baidu.com : negative / baidu.com : positive
```
判据：**v72.13 的 tpws / nfqws：文件存在但为空 = 匹配所有主机**。空名单不是「没生效」，而是「对全部域名 desync」。
**根因**：v72.13 发行包实物核对 + 实机日志得到的语义，旧文档「hostlist 为空等于未启用」对本机不成立；设备当前 hostlist 故意留空 = 全量 desync（机主本意）。
**修法 / 回滚**：
```sh
# [路由器] 要收窄到具体域名：写名单后重启（支持 # 注释行）
vi /opt/zapret/ipset/zapret-hosts-user.txt
/etc/init.d/zapret restart && /etc/init.d/zapret start_fw
# 回滚：uninstall-sni-desync.sh 会把名单备份到 /tmp/zapret-hosts-user.txt.bak，cp 回去即可
```
**已知未闭环**：`zapret-hosts-user-exclude.txt` 始终缺失（发行包只给 `...default`，安装脚本从未落盘）；且该机制会把条目当**域名**用 digger 解析（`ipset/def.sh` 的 `getexclude`），**填私网 CIDR 不一定生效**，所以守卫 2 改用 iptables `RETURN` 实现，没有依赖它。

### 3.6 tpws 模式下行被削半 —— 开启 SNI 分流后聚合下行明显下降（历史观测 500 → 270 Mbps），上行看起来不受影响。
**快速定位**：
```sh
# [路由器] 当前模式 + 用"转发路径 + 明文 HTTP"装置做对照（本机路径数字不可用于结论，见 §5.1）
grep -E 'NFQWS_ENABLE|TPWS_ENABLE|MODE_FILTER' /opt/zapret/config
sh CampusRedialWrt/kmod-build/remote/cr-fwd-client.sh   # 起真客户端装置
sh CampusRedialWrt/kmod-build/remote/cr-nfq-ab.sh       # 本机路径 A/B + daemon CPU 采样
```
判据（同一负载、同一靶站、同一条转发路径的实测对照）：
| 路径 | 聚合 | 说明 |
| --- | --- | --- |
| 经 tpws | **173.1 / 180.4 Mbps** | 转发路径 16 流 |
| 经 nfqws | **312.5 / 314.7 Mbps** | 同负载，**1.77×** |
| 完全不经手（`nozapret` 排除） | **355.05 Mbps** | 本地路径 16 流对照 |
**根因**：tpws 是**用户态透明代理**，**两个方向**的载荷都要 `read()/write()` 过一遍用户态 + 本地回绕，没有「只处理上行、下行直通」这种模式。（旧记录里「上行是内核直通、只有首包走 tpws」**是错的**：上行看着无损，只因**上行线速率 250 Mbps 低于 tpws 天花板**，而下行 500 Mbps 高于它。更准确的口径是 tpws 受**中继效率**限制：162~207 Mbps 时它只占 0.34~0.47 个核，**还没到 CPU 打满**就被中继路径限制住了。）
**修法 / 回滚**：切 nfqws（本项目已完成，无需换设备）。
```sh
# [路由器] 回到 tpws（反向即切 nfqws）；脚本用法：cr-nfq-switch.sh on|off|status
cp /opt/zapret/config.tpws.bak /opt/zapret/config
/etc/init.d/zapret stop_fw; /etc/init.d/zapret restart; /etc/init.d/zapret start_fw
# [路由器] 连内核模块一起卸（彻底回滚）
opkg remove iptables-mod-nfqueue kmod-ipt-nfqueue kmod-nfnetlink-queue
rmmod xt_NFQUEUE nfnetlink_queue
```
代价必须告知：切回 tpws 后下行会重新被削到 ~173~180 Mbps 量级；彻底关掉分流后，原来需要 desync 才能访问的站点可能又不可达。

### 3.7 聚合下行卡在 ~350 Mbps（开不开分流都一样）—— 多拨 5 条会话、每条单独都能跑到 ~175~212 Mbps，但**并发**下载总量只有 340~360 Mbps，且读数在 300/400/500 之间乱跳。
**快速定位**（关键：先判断"是不是路由器 CPU"）：
```sh
# [路由器] 1) 边打流边看 CPU：busy 99%+ 且 softirq 占大头 ⇒ 瓶颈是每包走慢路径的 CPU
#    采样器在仓库里：CampusRedialWrt/kmod-build/remote/cr-cpu-sample.sh
sh cr-cpu-sample.sh 20 >/tmp/cpu.log 2>&1 &            # 每秒采一次 /proc/stat
# 打流期间把 /tmp/cpu.log 取回，逐秒算 100-idle-iowait，并看 cpu0/cpu1 是否有一核钉在 100%
# → PC 侧装置（含四个测量坑的规避）：CampusRedialWrt/tools/measure-aggregate.ps1
# [路由器] 2) 确认快路径没被用上：xt_FLOWOFFLOAD 引用计数为 0 且 FORWARD 里没有 FLOWOFFLOAD 规则
lsmod | grep -E 'xt_FLOWOFFLOAD|nf_flow_table'
iptables -t filter -S FORWARD | grep FLOWOFFLOAD || echo "没有快路径规则"
# [路由器] 3) 排除"校园网/测速服务器只有 350M"：单流直连同一服务器可达 244 Mbps（RTT 1.5 ms）
curl -s -o /dev/null -w '%{speed_download} B/s\n' 'http://test.xidian.edu.cn/backend/garbage.php?ckSize=100'
```
**判据**：打流时 `cpu1` 100%、softirq ~92%，而各会话速率远低于各自的 200 Mbps 通道上限
（实测 14 / 57 / 115 Mbps 那种）⇒ **是路由器转不动，不是校园网给不出**。

**修法**（实测 350 → 700 Mbps，且不影响 desync）：
```sh
# [路由器] 安装转发快路径 + 首包保护（幂等，注册 fw3 include，reload/重启后自动补回）
sh install-flow-offload.sh            # 来自 release 的 sni-desync 包 / CampusRedialWrt/tools/
sh install-flow-offload.sh --dry-run  # 先看动作
sh install-flow-offload.sh --uninstall
```
**为什么必须三条规则而不是一条**：一条裸 `-j FLOWOFFLOAD` 会让 TCP 在三次握手完成时就进快路径，
nfqws 再也看不到 ClientHello（实测 NFQUEUE 命中数为 **0**），**混淆静默失效但带宽看起来正常**——
这是最危险的失败模式。把 80/443 的前 8 个原始方向包留在慢路径即可两全。
**验收**：下载期间 `iptables -t mangle -L POSTROUTING -v -n | grep NFQUEUE` 的包计数应持续增长
（约 4.5 包/连接）；带宽应到 ~690 Mbps 量级；`cpu1` 峰值降到 ~70%。

**顺带解释"浮动"**：mwan3 的 `cr_balanced` 是**按连接随机**分配（每连接 20% 概率落到某条会话），
连接数少时分布很不均（实测同样 10 条流：`77.7/155/155.5/155.2/77.7` 与 `37.5/197.9/132.3/130.3/111.7`）。
单次测速读数本来就跳；**别用单次数字下结论，用多轮 + 高连接数**。

> 测量方法坑（务必一起看）：测速端点若像 LibreSpeed 的 `garbage.php` 那样**不带 `ckSize` 只回 4 MB**，
> 就会把结果变成"N×4MB ÷ 窗口"的假象（实测 5/20/40 条流得到 15.8 / 63 / 126 Mbps，
> 而 curl 自报 408~836 Mbps——两个数字都不是吞吐）。带 `?ckSize=100` 才是持续流。

### 3.8 取消「开机自启」后，一次防火墙 reload 把接管规则悄悄摘掉 —— 面板显示「nfqws 在运行，但 mangle 里没有 NFQUEUE 规则」，服务状态却是"运行中"。
**原因**：`/etc/firewall.zapret` 的守卫原先只认"自启软链存在"，而面板的「开机自启」复选框正是改这个软链。
于是"取消自启 + 进程还在跑"的中间状态下，任何一次 fw3 reload（接口 up、改配置、`/etc/init.d/firewall reload`）
都会**不补接管规则**，分流静默失效（进程还在，面板看着像正常）。
**判据与修法**：
```sh
# [路由器] 现场特征：软链没了、进程在跑、规则数为 0
ls -l /etc/rc.d/S21zapret 2>/dev/null || echo "无自启软链"
pidof nfqws || pidof tpws; iptables -t mangle -S | grep -c NFQUEUE
# 立刻恢复：等价于面板点「重启服务」
/etc/init.d/zapret start_fw
# 根治：让守卫在“进程仍在跑”时也补规则（install-sni-desync.sh 生成的模板已含此例外）
grep -q 'pidof tpws' /etc/firewall.zapret && echo "已含例外" || echo "旧模板，重跑 install-sni-desync.sh 或补该例外"
```
实测（本机）：取消自启 + `pidof nfqws` 有值 → `/etc/init.d/firewall reload` 后 **NFQUEUE 仍有 20 条、
flow offload 仍有 3 条**、状态 `running:true, enabled:false, redirect_kind:"nfqueue"` ✓。

> 顺带记住这个故障态的通用形态：**"进程在跑但没接管流量"**。除本条外，还有两个来源：
> `/var/run/zapret.off` 停止标记仍在（点过「停止」没点「启动」）、以及新会话上线后规则没补上
> （规则数 < 会话数×4）。三者都用「重启服务」恢复。

### 3.9 某应用/游戏开着分流就不正常（登录转圈、更新卡住、连接被重置）—— 先判断它到底在不在分流的适用范围里。
**适用范围（实测口径）**：只处理 **TCP 80、TCP 443、UDP 443** 三个端口（`nfqws` 的
`--filter-tcp=80/443`、`--filter-udp=443`），外加下行 `--sports 80,443` 的前 3 个回包。
**非这几个端口的流量一个包都不会进 NFQUEUE**。

```sh
# [路由器] 判据一：看规则实际匹配什么端口
iptables -t mangle -S | grep NFQUEUE | grep -oE '\-\-(d|s)ports [0-9,]+' | sort | uniq -c
#   期望：--dports 443(UDP) / --dports 80,443(TCP 出向) / --sports 80,443(TCP 回包)

# [路由器] 判据二：清零计数器后复现问题，看计数动不动（动=确实被分流处理了；不动=与分流无关）
iptables -t mangle -Z POSTROUTING; iptables -t mangle -Z FORWARD
# …此时复现异常（登录/进游戏）…
iptables -t mangle -L POSTROUTING -v -n | grep 'multiport dports 80,443'   # 出向命中
iptables -t mangle -L FORWARD -v -n | grep 'multiport sports 80,443'      # 回包命中
```

| 判据二的结果 | 结论 | 去看 |
| --- | --- | --- |
| 计数完全不涨（端口不在 80/443） | **与 SNI 分流无关**。游戏的 UDP 自定义端口本来就不被处理 | 多拨/mwan3（§2.1）、会话重拨打断、链路延迟 |
| 计数在涨（走 443 的登录/更新/反作弊） | 该连接确实在被 desync，可能被激进策略影响 | 本节下面的排除办法 |
| 用 UDP 443 的游戏异常 | 命中的是 QUIC 档（`fake` + `--dpi-desync-repeats=6`，头几个包被复制多份） | 同上 |

**排除办法（按 IP，可持久）**：NFQUEUE 规则本来就带 `! --match-set nozapret`（出向看 `dst`、
回包看 `src`），所以把目标 IP 放进 `nozapret` 即可让该连接彻底绕过分流：
```sh
# [路由器] 临时验证（重启 zapret 后丢失）
ipset add nozapret 203.0.113.7
# [路由器] 持久：逐行写 IP/CIDR，然后重启 zapret 让集合重新灌入
echo 203.0.113.7 >> /opt/zapret/ipset/zapret-ip-exclude.txt
/etc/init.d/zapret restart
# 回滚：删掉该行 / ipset del nozapret 203.0.113.7
```
实测（`iptables -t mangle -Z` 清零后各 5 条 HTTPS 到同一 IP）：未排除 **45/34 包**（上/下行），
已排除 **8/0 包**（8 是 0.5 s 窗口内的后台噪声），且请求全部 `200` ✓。

> 更彻底的做法是**别用空 hostlist**：把 `zapret-hosts-user.txt` 改成只列真正需要解限速的域名，
> 游戏等其它流量自然不会进 desync。代价是失去"对全部域名生效"（本机当前用法）。

### 3.10 池子频繁重拨时，`NFQUEUE` 规则被摘掉且不再补回 —— SNI 分流静默失效 —— 现场表现：`nfqws` 进程在跑、面板"服务状态"也算正常，但 `iptables -t mangle -S | grep -c NFQUEUE` 是 **0**（会话 5 条都在），此时**任何流量都没有被接管**。
**机理**：zapret 的规则由 `/etc/hotplug.d/iface/90-zapret` 在 WAN 接口 up/down 时重载。
池子在重拨（会话失败 → 断开 → 重新拨号）时，会话会反复 down/up；如果**最后一次事件是 down**，
`stop_fw` 摘掉规则之后不会再有 up 事件来补 ⇒ 规则永久缺失。实测本机就出现过：5 条会话都在、
`nfqws` 在跑，而 NFQUEUE 规则 **0 条**（此前是 20 条）。

```sh
# [路由器] 判据：规则数应等于「在线会话数 × 4」（每会话 tcp+udp 出向、tcp 入向 FORWARD/INPUT）
echo "会话: $(ip -4 -o addr show | grep -c pppoe)  规则: $(iptables -t mangle -S | grep -c NFQUEUE)"
# 立刻恢复
/etc/init.d/zapret start_fw
# 核对覆盖的接口
iptables -t mangle -S | grep NFQUEUE | grep -oE '\-o pppoe-wan[0-9]*' | sort -u
```
**根治方向（尚未实现）**：让守护进程在每次会话 up 之后、以及巡检周期里**校核并补齐** zapret 规则
（判据同上：少于在线会话数×4 就跑一次 `start_fw`）。当前版本仍需要人工点面板「重启服务」或执行
上面那条 `start_fw`。注意池子在 churn 时改 iptables 会撞 `xtables lock`（实测报
`Another app is currently holding the xtables lock`），实现时应用 `-w` 退避。

## 4. 内核模块 / ABI 类

### 4.1 `insmod` 成功，一建接口就 panic —— `vermagic` 完全一致（`5.4.164 SMP preempt mod_unload ARMv7 p2v8`）、`.plt` 段存在、`CONFIG_MODVERSIONS` 与 `CONFIG_MODULE_SIG` 均未启用 ⇒ `insmod` **成功**、`lsmod` 能看到模块；但一执行 `ip link add ... type macvlan` **立即 panic**：
```
PC is at mmiocpy+0xf0/0x330
(mmiocpy) from (get_random_bytes+0x8c/0xdc)
(get_random_bytes) from (macvlan_common_newlink+0x358/0x3b4 [macvlan])
```
**快速定位**：
```sh
# [路由器] 1) 是否 oops/panic（看 tainted 与 dmesg，别只看 logread，见 §4.4）
cat /proc/sys/kernel/tainted                       # 128 = TAINT_DIE
dmesg | grep -iE 'oops|Call trace|pc is at' | tail -20
# [WSL] 2) 上机前就该做的离线 ABI 判定（不碰路由器）
wsl.exe -d Debian -- bash /mnt/d/CampusNetworkRedial/campus-network-redial/CampusRedialWrt/kmod-build/wsl-final.sh
```
判据：必须看到 `netdev_priv` 命中 `#1408 ; 0x580`、`sizeof(net_device)=1408`、`offsetof(pcpu_refcnt)=0x2f8`，且厂商模块里 `0x2f8` 命中、`0x2b8` 为 0。
**根因**：社区预编译 `macvlan.ko` 声明 `kernel (= 5.4-qsdk-11.5.0.5-1-6be5791b…)`，与本机指纹 `1d36e0ba…` 不同（设备上 39 个已装 kmod 全部声明后者）。更深一层：**设备内核是 Qualcomm QSDK 厂商内核树**（`linux-ipq-5.4` @ `d5fcb18e…`），**不是上游 `linux-5.4.164`** —— 所以「设备原装 config + 上游源码」编出的 `.ko` **一定** ABI 不匹配，与 `olddefconfig` 无关，是**源码层面** `struct net_device` / `struct net_device_ops` 长得就不一样。布局不同 ⇒ `macvlan_common_newlink()` 内联的 `eth_hw_addr_random()` 从错误偏移取 `dev->dev_addr`（读到近似空指针 `0x1`），`get_random_bytes(0x1, 6)` 写坏内存 → panic；`CONFIG_MODVERSIONS` 未开、`vermagic` 又恰好相同，所以 `insmod` 会成功 —— **最危险的一类不兼容**。
量化：`sizeof(struct net_device)` 上游 **1344** vs QSDK **1408**，**差 64 字节**（`WIRELESS_EXT` 两指针 +8、`priv_flags_ext` +4、`local_addr_mask` +32、`_tx` 的 cacheline 对齐填充 +20）；`struct net_device_ops` 264 vs 272，新增两个 offload 钩子插在 `ndo_bridge_dellink` 之后 ⇒ `ndo_change_carrier` 之后（含 macvlan 会设置的 `ndo_get_iflink`）整体错位 8 字节，是**第二个崩溃源**。
**修法 / 回滚**：用**厂商 QSDK 源码**重编（流程见 `docs/reference/AX3000-KMOD-BUILD.md` §6）。出事后先止损：
```sh
# [路由器] 确认危险模块不在设备上；期望 modprobe 变成 255（明确失败，而不是带病可用）
lsmod | grep macvlan
rm -f /lib/modules/5.4.164/macvlan.ko /etc/modules.d/30-macvlan; rmmod macvlan 2>/dev/null
modprobe macvlan; echo "rc=$?"
ifup wan && ip -4 addr show pppoe-wan && ip route | grep '^default'
```
`/etc/config/network` 备份在设备 `/etc/config/network.campus-redial.bak`。**未刷固件、未改动固件分区** —— 这类故障不需要动固件。
> ⚠️ ABI 未对齐时**任何内联访问（哪怕只读）都可能崩内核**：只读探针 `cr_abicheck.ko` 自己也把内核打崩了（退出路径上的 `dev_put()` 按上游偏移取 `dev->pcpu_refcnt`，而设备上 `0x2b8` 处并不是它）。所以**不要**用「先上机试一下」判定 ABI，用上面的离线判定。

### 4.2 `module PLT section(s) missing` —— 借用其它 target 的 kmod 时 `macvlan: module PLT section(s) missing`。
**快速定位**：
```sh
# [路由器] 期望 CONFIG_ARM_MODULE_PLTS=y
zcat /proc/config.gz | grep ARM_MODULE_PLTS
# [WSL] 看模块有没有 .plt 段
readelf -SW <module>.ko | grep -i '\.plt'
```
判据：本机 `CONFIG_ARM_MODULE_PLTS=y`，而官方 21.02.7 的 armv7 内核**没开**该选项 ⇒ 官方编出的 `.ko` **没有 `.plt` 段** ⇒ 被模块加载器拒绝。
**根因**：两种不匹配叠加 —— **vermagic 不同**（`5.4.238` vs `5.4.164`）+ **缺 `.plt` 段**（`armvirt/32`、`ipq40xx/generic` 等 target 的内核未开 `ARM_MODULE_PLTS`）。
**修法 / 回滚**：不要借别的 target 的 kmod，用与设备**同源**的厂商 QSDK 源码自编（本机内核开了该选项，模块加载器会在需要时自动分配 PLT，编出的模块自然带 PLT）。回滚：删掉借来的 `.ko` 与 `/etc/modules.d/` 条目即可（它们从未加载成功，风险低于 §4.1）。

### 4.3 `Unknown symbol` —— `insmod` 报 `Unknown symbol ...`，看起来像依赖没装。
**快速定位**：
```sh
# [路由器] 用 kallsyms 对照；本机没开 KALLSYMS_ALL，只有函数符号 ⇒ 数据符号查不到属正常
grep -w '<符号名>' /proc/kallsyms ; zcat /proc/config.gz | grep KALLSYMS_ALL
```
判据：**查不到的「缺失符号」全是数据符号**（`nf_ct_hook` / `nfnl_ct_hook` / `init_user_ns` / `kmalloc_caches` / `__stack_chk_guard` / `nfnl_lock` / `nfnetlink_*` 等）⇒ 不是真缺失。
**根因**：设备**没开 `KALLSYMS_ALL`**，`/proc/kallsyms` 只列函数不列数据。按**函数符号命中数**判定即可（实测 `nfnetlink_queue` 61/66、`xt_NFQUEUE` 9/10 命中）；数据符号改用**厂商树里的 `EXPORT_SYMBOL` + 提供方 `CONFIG_*` 在设备上确实已构建**来证明。
**修法 / 回滚**（纯校验，无需回滚）：
```sh
# [WSL] 重跑闸门；零件：static-check.sh / config-drift.sh / config-diff-lf.sh / missing-syms.sh
wsl.exe -d Debian -- bash /mnt/d/CampusNetworkRedial/campus-network-redial/CampusRedialWrt/kmod-build/wsl-nfq-verify.sh
```
若确实缺**函数**符号，才是真依赖问题（需把提供方编进同批模块或调整 QSDK 树配置）。

### 4.4 怎么判断设备是否 oops / 抓 panic 日志 —— 曾误报「0 oops」—— 只跑了 `logread | grep oops`，而 `logread` 的环形缓冲已把那行冲掉。
**快速定位**：
```sh
# [路由器] 权威口径一：tainted 位（0 = 干净；128 = TAINT_DIE，近期有过 oops/BUG）
cat /proc/sys/kernel/tainted
# [路由器] 权威口径二：dmesg（不是 logread）
dmesg | grep -iE 'oops|BUG|Call trace|Internal error' | tail -30
# [路由器] 模块 init 有没有跑完（半初始化态特征）：坏是 coming，而不是 live
cat /sys/module/<模块名>/initstate ; lsmod | grep <模块名>
```
判据：`tainted` 含 **128** ⇒ 有过 oops/BUG，哪怕 `logread` 里什么都看不到；`initstate=coming` + `refcnt` 非 0 ⇒ 模块卡在半个初始化态、**`rmmod` 不掉**。
**根因**：`logread` 是环形缓冲，早于当前窗口的 oops 会被冲掉，`dmesg`（`/dev/kmsg`）才是完整来源。实测：一次 `cr_abicheck` 在 `init` 里挂掉（`print_hex_dump` 读坏地址），内核**没死**（`uptime` 连续、无 panic），`tainted=128` 且**只有这一位**，模块从此卡在 `coming`、白占约 28 KB。
**修法 / 回滚**：
```sh
# [路由器] 1) 先关掉自动重启（kernel.panic=3 会 3 秒后重启，来不及看日志）；判据 0
sysctl -w kernel.panic_on_oops=0 ; cat /proc/sys/kernel/panic_on_oops
# [Windows] 2) 双通道抓取：一条持续读 /dev/kmsg 并 fsync 落盘，另一条触发 insmod
C:/Users/Tyuikl/.workbuddy/binaries/python/envs/default/Scripts/python.exe C:/Users/Tyuikl/.campus-ssh/kmsg-capture.py
# 仓库侧同款：CampusRedialWrt/kmod-build/kmsg-capture.py
# [路由器] 是否重启后复发：期望 modules.d 里没有诊断模块、rc.local 只有 exit 0、无 crontab
ls /etc/modules.d/ ; cat /etc/rc.local ; crontab -l 2>/dev/null
```
半初始化态模块（`initstate=coming`）**只能靠重启**清理；删内核模块属严肃更改，先确认再动。回滚：`panic_on_oops` 恢复原值（注意**重启会把恢复动作抹掉**，设备当前实测是 0）。

## 5. 测量方法学陷阱（测错了会得出错的结论）

### 5.1 路由器本机跑 TLS 测不出代理天花板 —— 12 路 HTTPS 从路由器本机测，聚合只有 **79 Mbps**，于是误判「tpws 上限就是 80」。
**快速定位**：
```sh
# [路由器] 本机路径下路由器自己是 TLS 客户端，CPU 成本全算在它头上
grep -E 'DNAT|--to-destination 127.0.0.127' /etc/firewall.zapret ; iptables -t nat -S | grep -c 988
```
判据：本机路径数字**是**经 tpws 的数字（zapret 在 tpws 模式下给每个 WAN 设备装了 `nat OUTPUT -o pppoe-wanN -m owner ! --uid-owner 1 … -j DNAT --to 127.0.0.127:988`），但**本机跑 TLS 会先把自己 CPU 吃满**（12 路 HTTPS 只有 79 Mbps 时 tpws 仅占 0.115 核）⇒ 用 HTTPS 从本机测**永远摸不到 tpws 天花板**。
**根因 / 正确做法**
1. 用**明文 HTTP 大文件**测，本机 TLS 成本归零。
2. 测「代理路径」必须有**真正的转发流量**（LAN 客户端 → 路由器 → WAN），用 `CampusRedialWrt/kmod-build/remote/cr-fwd-client.sh`。
3. **别自己往 `nat OUTPUT` 加镜像规则**：漏掉 `-m owner ! --uid-owner 1` 会把 **tpws 自己发出的连接**再 DNAT 回 tpws（死循环），症状是 `curl: (35) SSL_connect failed with error -308` 且规则计数暴涨。
4. 绕过 tpws 做实时对照：`ipset add nozapret <ip>` 立刻生效（DNAT 规则本来就带 `-m set ! --match-set nozapret dst`），`ipset del` 即恢复，不用改配置、不用重启。注意 `create_ipset` 是 `no-update` 调用，**集合已存在时不会被重灌**，手工条目能存活到重启。
**修法 / 回滚**：
```sh
# [路由器] 删对照条目并核对测试残留；期望 mangle PREROUTING 只剩 mwan3_hook、nat 里 199xx 计数 0
ipset del nozapret <ip> ; iptables -t mangle -S PREROUTING ; iptables -t nat -S | grep -c 199
```

### 5.2 macvlan 子接口挂在桥设备上时，子→父不通 —— `ip netns` + 单个 macvlan 做客户端、网关写 `192.168.6.1`（`br-lan`），结果 **100% 丢包**。
**快速定位**：
```sh
# [路由器] 判据：ping 父接口地址 100% 丢包（不是防火墙问题，别去改 iptables）
ip -d link show | grep -A2 macvlan ; ip netns exec <ns> ip route
ip netns exec <ns> ping -c 2 192.168.6.1
**根因**：macvlan 子接口挂在 `br-lan`（桥设备）上时**子→父不互通** —— 父设备 TX 走桥端口，不会回灌给子接口，所以不能拿 `br-lan` 当网关。

# [路由器] 起装置 / 收工
sh CampusRedialWrt/kmod-build/remote/cr-fwd-client.sh
# 回滚核对（实测通过的口径）：期望无 netns、无 crgw0/crns0、nat/FORWARD 无 10.9.9/crgw0 规则
ip netns list ; ip link show | grep -E 'crgw0|crns0' ; iptables -t nat -S | grep -c 10.9.9
```

### 5.3 `/proc/PID/stat` 的 comm 含空格会让 `awk` 错位 —— 采样 daemon CPU 时算出「tpws 烧满一个核」，与「中继路径受限」的实测矛盾。
**快速定位**：
```sh
# [路由器] 看 comm 字段有没有空格/括号；坏的写法字段会整体错位
head -c 200 /proc/$(pidof tpws)/stat
awk '{print $14,$15}' /proc/$(pidof tpws)/stat                    # 坏
cut -d')' -f2- /proc/$(pidof tpws)/stat | awk '{print $12,$13}'   # 好
```
判据：comm 形如 `(campus-rediald)` 这类**含空格或有额外 token** 时，`$14/$15` 不再是 `utime/stime`。修正解析后实测 tpws 是 **0.34~0.47 核**，不是 1 核。
**根因**：`/proc/<pid>/stat` 第 2 字段 `comm` 被括号包裹且**可包含空格**，按空白切分会让其后字段编号整体漂移；正确做法是先 `cut -d')' -f2-` 丢掉前半段，再用固定偏移取 `utime/stime`。
**修法 / 回滚**：改用上面的正确姿势（`CampusRedialWrt/kmod-build/remote/cr-nfq-ab.sh` 已按此采样）。无回滚。

### 5.4 `set -o pipefail` 下 `生产者 | grep -q` 的 SIGPIPE 假阴性 —— ABI/配置闸门**静默**报成「配置不一致」（一次误报 5 个符号），而实际配置一致。
**快速定位**：
```sh
# [路由器/WSL] 在闸门脚本里找形如 生产者 | grep -q 的判据；判据是 grep 命中即退出，生产者收 SIGPIPE(141)
grep -n 'grep -q' <闸门脚本>
```
**根因**：`set -o pipefail` 下管道任一环节非 0 即整条失败；`grep -q` 一命中就退出，上游（`tr`/`cat` 等）写不完被 SIGPIPE 杀掉 ⇒「命中」反被报成「失败」。
**修法 / 回滚**：判据里**不要出现 `生产者 | grep -q`** —— 把输出落到变量/临时文件再比，或改用 `grep -c` + 数值比较。无回滚。

### 5.5 字符串比较前的裁剪（vermagic 尾空格 / config CRLF） —— 两个模块的 vermagic「看起来一模一样」，字符串比较却始终不相等。
**快速定位**：
```sh
# [WSL/路由器] 必须裁剪尾空白后再比；不裁剪时 vermagic= 行带尾空格，直接比较会假报不同
strings <module>.ko | grep '^vermagic=' | sed 's/[[:space:]]*$//'
# [WSL] 设备导出的配置是 CRLF（实测 4633 个 \r），带 \r 会让 grep '^CONFIG_X=' 全变"不一致"
tr -d '\r' < config-5.4.164-ax3000 | grep '^CONFIG_ARM_MODULE_PLTS='
```
**修法 / 回滚**：统一 `sed 's/[[:space:]]*$//'` 裁尾空白、`tr -d '\r'` 去 CR（仓库零件 `config-diff-lf.sh` / `cfgfmt.sh` 就是干这个的）。无回滚。

### 5.6 SSH 回来的输出带 CRLF —— `echo $((s / 1000))` 报 `bash: invalid arithmetic operator (error token is "\r")`。
**快速定位**：
```sh
# [Windows] 先确认返回串里是否有 \r；有就直接进 $(( )) 必报该错
ssh root@<ip> 'cat /var/run/campus-redial/speed.value' | od -c | tail -2
```
**修法 / 回滚**（任选）：
```sh
# [Windows] ① 先去掉 \r
s=$(ssh root@<ip> 'cat /var/run/campus-redial/speed.value' | tr -d '\r')
# [Windows] ② 更好：把算术放在设备上算，只把结果拿回来
ssh root@<ip> 'echo $(( $(cat /sys/class/net/pppoe-wan/statistics/rx_bytes) / 1000 ))'
```
同批测量脚本踩过的同类坑：**下载要看 WAN 口的 `rx_bytes` 而不是 `tx_bytes`**（`tx_bytes` 只统计上行/ACK，用它算下载速率会得到 ~1 Mbps 的荒谬结果）；`date +%s` 只有秒级精度、用它算 `elapsed` 误差可达 ±17%，要精确用 `date +%s.%N` 或固定时间窗 + 路由器计数器；宿主机若有 `http_proxy/https_proxy`（本项目开发机有 `http://127.0.0.1:58561`）测速必须 `--noproxy '*'`，否则 `--interface`/`--resolve` 全部失效；Windows Git Bash 的 curl **不认 `-o /dev/null`**（rc=23、size=0），要用 `-o NUL`。无回滚。

### 5.7 Windows 浏览器测得 200 Mbps，路由器上只测到 60 Mbps —— 浏览器测速约 200 Mbps，路由器上只测到 60 上下，怀疑算错了。
**快速定位**：
```powershell
# [Windows] 看这台机器几条默认路由、谁胜出
netstat -rn | Select-String '0.0.0.0' ; netsh interface ipv4 show interfaces
```
判据（实测）：
| 目的地 | 网关 | 接口 | 度量 |
| --- | --- | --- | --- |
| `0.0.0.0/0` | `10.198.255.254` | WLAN（校园网） | **10 ← 胜出** |
| `0.0.0.0/0` | `192.168.6.1` | 以太网（本项目路由器） | 50 |
Windows 取**最小 metric** ⇒ **浏览器测速默认走校园 WLAN，从来不经过 AX3000**。不是算错，是**测错了层**。
| 路径（同一时刻实测） | 结果 |
| --- | --- |
| 校园 WLAN 单 IP，1/2/4/8 条并行流 | 79 / 88 / 92 / 95 Mbps ⇒ **单 IP 天花板 ~95 Mbps**，与并发数无关 |
| 经路由器、**只要转发**（PC 做 TLS），单会话 | ~96 Mbps 峰值（短时，30 MiB 约 2.6 s） |
| 经路由器，单会话，**15 s 持续窗口** | **~41 Mbps** ⇒ 单条 PPPoE 会话 ≈ 40 Mbps 持续（有突发，像令牌桶） |
| 经路由器，**三会话各 1 条流**，15 s 窗口 | **117 Mbps**（重测 119）⇒ 几乎正好 3× |
**修法 / 回滚**：**双宿主机（dual-homed）不能用 `curl --interface <IP>` 强行换路** —— SYN 能到路由器、SYN-ACK 也回来了，但 PC 侧连接卡在 `SYN_RECV`（去程按 metric 10 走 WLAN、回程从以太网进来被丢弃）。**绕法**：在路由器上做 DNAT，让 PC 连 `192.168.6.1:<port>`，目的地 on-link、不走默认路由竞争，TLS 端到端由 PC 完成，路由器只转发 —— **这才是「测路由器转发能力」的正确姿势**。要让 PC 整体走路由器需临时改 metric 或加 `/32` 路由（**需管理员**）；回滚即删掉临时 DNAT 与 `/32` 路由、改回 metric。

### 5.8 Windows 侧脚本报属性 `Mbps` 找不到 —— `Redial-UntilCampusReady.ps1: 无法找到属性 "Mbps"`。
**快速定位**：
```powershell
# [Windows] 在测量函数里找没有接收返回值的 .NET 方法调用；没被 [void]/$null 吞掉就是命中
Select-String -Path Redial-UntilCampusReady.ps1 -Pattern 'EnsureSuccessStatusCode'
**根因**：`HttpResponseMessage.EnsureSuccessStatusCode()` **返回响应对象**；PowerShell 里未被赋值的返回值会**发射到管道**，于是测量函数返回「响应对象 + 结果对象」的**数组**，调用方取 `.Mbps` 自然取不到。

# [Windows] 在 Measure-XidianBandwidth 里显式丢弃该返回值
[void]$resp.EnsureSuccessStatusCode()
```

### 5.9 路由器自测总是偏低、筛不出 200 Mbps 通道 —— 同一台机器：PC 测得 200 Mbps、路由器只测到 60~95 Mbps，而"逐会话测速"每条会话读数都差不多。
**快速定位**：
```sh
# [路由器] 1) 测速流量真的钉在那条会话上了吗？
ip rule | grep -E 'iif |fwmark'          # mwan3 的规则：`iif <dev> lookup N` 与 `fwmark 0xN00/0x3f00 lookup N`
SRV=<测速服务器IP>; IP2=$(ip -4 -o addr show dev pppoe-wan2 | awk '{print $4}' | cut -d/ -f1)
ip route get $SRV from $IP2              # dev 不是 pppoe-wan2 ⇒ 源地址绑定对它没有选路作用
# [路由器] 2) 绑 wan2 的源地址下载，看哪条会话的计数在涨
b2=$(cat /sys/class/net/pppoe-wan2/statistics/rx_bytes); b4=$(cat /sys/class/net/pppoe-wan4/statistics/rx_bytes)
curl -sS -4 --interface "$IP2" --max-time 6 -o /dev/null "http://$SRV/backend/garbage.php?ckSize=100"
echo "wan2=$(( $(cat /sys/class/net/pppoe-wan2/statistics/rx_bytes) - b2 ))  wan4=$(( $(cat /sys/class/net/pppoe-wan4/statistics/rx_bytes) - b4 ))"
```
判据：`ip route get` 的 `dev` 与源地址所属会话不一致，或下载时**别的会话**计数在涨 ⇒ 测速没有钉住会话。

**根因**（三者叠加，全部实测）：
1. **只绑源地址钉不住会话**：内核按**主路由表**选路，而 mwan3 是按 **fwmark** 选表 ⇒ 出现"源 IP 属于 A 会话、流量从 B 会话出去"，非对称包被丢弃/限速。`campus-redial-bind.so`（`SO_BINDTODEVICE`）缺失时就是这个状态。
   实测：把 curl 绑到 wan2 的源地址下载，**103.6 MB 全部从 `pppoe-wan4` 进来**（wan2 增量 0.00）⇒ 所谓"逐会话测速"其实一直在测主默认路由那一条。
2. **HTTPS 会让路由器自己成为瓶颈**：双核 A7 跑 6 路 TLS 只有约 **79~105 Mbps**。同一组会话对照：明文 HTTP 测得 `96 / 210 / 209 / 100 / 101` Mbps，HTTPS 测得 **99.9~104.9 Mbps（全部被压平）** ⇒ 200M 通道被读成 100M，**HTTPS 口径根本无法区分两类通道**。
3. **单流 + 短窗口 + 不丢暖机**：同一条会话单流只有 **15.9 Mbps**、6 流聚合 **212.1 Mbps**；5 秒窗口还把 TCP 慢启动算进平均值。

**修法 / 回滚**：`campus-rediald` 的 `run_speed_test_session()` 已在 **1.0.0-4** 重做：
- 测速前按会话**追加**一条 `mangle OUTPUT -p tcp --dport <测速端口> -m owner --uid-owner 0 -j MARK --set-xmark <mark>/0x3f00`，测完删除。**必须追加**：`mwan3_hook` 是 `mangle OUTPUT` 的第 1 条，它会清掉已有 mark。mark 从 `ip rule ... iif <dev> lookup N` 反查（`mark = N << 8`），不写死。
- 口径改为**会话接口 `rx_bytes` 增量**：**先暖机 3 秒**，再取 `bandwidth_test_seconds`（建议 6）秒窗口；worker 自报字节数只作交叉校验写进日志（它含慢启动段，天然偏低）。
- **只测一轮**（2026-09-11 起按用户要求）：窗口 6 s + 暖机 3 s，读数即判据；历史上曾两轮取大值以对冲令牌桶抖动，现已去掉（与面板/浏览器看到的一次测速一致）。
- 测速 URL 用 **`http://`**；阈值 `bandwidth_threshold_mbps` 用 **150**（100M 通道实测 96~103，200M 实测 173~212）。
- 手动复现/自查脚本：`CampusRedialWrt/kmod-build/remote/cr-speed-probe.sh`（同一轮里给出 HTTP 与 HTTPS 两套读数，可直接对比）。

回滚：把 `bandwidth_test_uri` 改回 `https://…`、`bandwidth_threshold_mbps` 改回 `100`，即回到旧行为（但"筛不出 200M 通道"会重现）。

> **⚠️ 换了测量口径或阈值之后，必须强制一整轮重测，否则会看到新旧混合的数字。**
> 池子的稳态清扫是"**只修不测**"：`session.<name>` 里 `verified=1` 且接口健康的会话会被直接跳过
> （唯一例外是 `mbps200=disabled` 时会强制重测）。所以升级到 1.0.0-4、或改了阈值之后，
> 那些在旧口径下就已 verified 的会话**不会自动重测**，面板上会留着旧数值。
> 强制全量重测（运行时状态在 tmpfs，重启即复原，无副作用）：
>
> ```sh
> # [路由器]
> /usr/sbin/campus-redialctl stop; sleep 3
> for n in wan wan2 wan3 wan4 wan5; do
>   f=/var/run/campus-redial/session.$n; [ -f "$f" ] && sed -i 's/^verified=.*/verified=0/' "$f"
> done
> rm -f /var/run/campus-redial/speed.*.value /var/run/campus-redial/speed.*.result
> /usr/sbin/campus-redialctl start
> # 之后约 20 s/会话；判为 100M 的会被重拨，直到全部落进 200M 通道
> ```
>
> 本机实测（1.0.0-4，5 会话）：`wan 83.71 → 重拨 → 176.42`，其余 173.65 / 174.13 / 175.59 / 175.42，
> 最终 `verified_count=5`、聚合 175.04 Mbps。

**顺带**：PC 侧的双宿主机坑见 §5.7（浏览器测速默认走校园 WLAN；双默认路由下 `curl --interface` 会卡 `SYN_RECV`）。
