## 0. 术语表

| 词 | 在本项目里的含义 |
| --- | --- |
| **出口** | 一次 PPPoE 拨号所获得的接入通道。校园网每次拨号可能落到不同的出口设备/策略组，质量不一样。 |
| **好出口 / 坏出口** | 好出口能正常访问你要用的服务；坏出口会对**部分服务**限速（表现为请求超时、加载不出来），但基础连通性还在。 |
| **会话（session）** | 一条独立的 PPPoE 连接。本项目的连接池就是"同一账号的多条会话"。 |
| **连接池（pool）** | 由多条会话组成的聚合出口，由 mwan3 按连接分摊流量。 |
| **desync** | 主动扰乱 TLS ClientHello 的发送方式，使链路中间的 DPI 读不到（或读错）SNI 域名。 |
| **hostlist** | desync 的域名名单。**留空 = 对所有域名生效**（实测语义，见 §7.4）。 |
| **探针（probe）** | 用来判断"当前出口好不好"的在线请求。 |
| **nfqws / tpws** | zapret 的两种工作模式：前者走内核 NFQUEUE（只把每连接前几个包送进用户态），后者是用户态透明代理（全部载荷过用户态）。 |

## 1. 问题：拨号出口的好坏是随机的

校园网通常用 PPPoE 接入。账号认证通过后，BRAS（本项目实测是华为 **ME60-X8A**）会把这次会话
分配到某个出口。实测现象：

- 好出口：一切正常；
- 坏出口：**基础连通性没问题**（ping 通、能打开部分网站），但对某些服务（实测中最典型的是
  一部分腾讯系服务）会被限速甚至直接不可用，表现为"某个应用就是加载不出来"。

对用户来说，最省事的应对不是去研究限速规则，而是**换一个出口**：断开、重新拨号，直到落在一个好出口上。
这就是本项目两部分功能的第一块——**出口检测 + 自动重拨**。

第二块是**带宽**：单条 PPPoE 会话的持续下行有一个上限（本项目实测在 **40~100 Mbps** 量级波动，
取决于时段与测速方式），而 BRAS **允许同一个账号建立多条会话**，于是多条会话 + 按连接分流
可以近似线性地叠加带宽（实测 **1.9× ~ 3×**）。这就是**多拨连接池**。

第三块是**对抗按 SNI 的限速**：坏出口的限速并不是"整个 IP 段全限"，而是按 TLS 握手里的
**SNI 域名**做黑名单。于是可以让 DPI 读不到 SNI，从而落回"不限速"的默认类别。这就是
**SNI 分流（desync）**。

## 2. 检测：怎么判断"这个出口好不好"

思路是**用真实业务做探针**，而不是看链路层指标（链路层在坏出口上也是通的，看不出问题）。

- **普通模式**：对一组探针地址做多轮 HTTP(S) 请求。每轮内多次请求**全部成功**才算这一轮通过；
  **连续三轮**（且中间有递增的等待间隔）都通过，才判定为"好出口"。这样做的原因是坏出口的表现
  往往是"时通时断"或"慢到超时"，单次成功不足以说明问题。
- **200 Mbps 模式**：直接从测速端点下载一段时间，按实际速率判断是否超过阈值（默认 150 Mbps）。
  它针对的是"出口没被限速但带宽不达标"的情况。
- 两种模式可以**同时启用**：两者都通过才算好出口，任一失败就重新拨号再测一遍。

判定通过后，程序/守护进程按策略停下（Windows 侧默认成功后退出，路由器侧进入 `success` 状态并
持续维护连接池）。

> **探针地址必须换成自己学校可达的地址。** 仓库里默认的探针（斗鱼 CDN 接口）与测速端点
> （西电的 `test.xidian.edu.cn`）只是实测环境的示例，在别的网络里很可能不可达。

## 3. 重拨状态机

两侧实现（Windows 的 C# 程序 / 路由器的 `campus-rediald`）逻辑一致，都是：

```
空闲 ──启动──▶ 拨号 ──拨通──▶ 静置等待 ──▶ 探测/测速 ──通过──▶ 成功（停止或保持）
                   ▲                              │
                   └────────── 失败且未达上限 ──────┘
                              （失败后等待一段时间再拨）
                   达到最大尝试次数 ──▶ 失败（停在 failed，不再无限重拨）
```

几个刻意的设计：

- **拨号后先静置再探测**：PPPoE 刚起来的一两秒里网络尚未可用，立刻探测会产生假失败。
- **失败重拨有间隔**：BRAS 对同一账号的两次认证有最小间隔限制（实测报错
  `E2532: The two authentication interval cannot be less than 3 seconds`），拨得太快只会连续认证失败。
- **有上限**：达到 `max_attempts` 就停在失败态，避免"永远在重拨"把用户网络搞得不可用。
- **忙时让路**：会话出口的秒级流量超过 `busy_threshold_kbytes` 时推迟检测，避免在用户正在下载时
  把会话拆掉。
- **只动自己该动的东西**：路由器侧只操作配置的 WAN 接口与本包自己创建的 `wan2..wan6` 派生接口，
  从不重启整个网络、不碰 LAN / 桥 / 无线 / LuCI / uhttpd。

## 4. 多拨连接池：为什么"同账号多会话"能成立

### 4.1 关键实测结论

| 结论 | 实测依据 |
| --- | --- |
| 同一账号**允许多路并发**，前提是**源 MAC 不同** | 用临时 macvlan + 手工 `pppd` 起第二条会话：**4 秒拨通**，拿到**独立 IP**，主会话全程不受影响 |
| **同 MAC 多会话被禁止** | 第二条会话一出现，BRAS 立刻发 `PADT` 把原会话踢掉 |
| **VLAN 多拨不通** | 带 802.1Q 标签的 PADI 到不了 BRAS（`PADO` 永远超时），即使把 VLAN id 置 0 也会被插 4 字节标签后被丢弃 |
| 所以每条会话都要"独立 MAC + 不带标签的以太帧" | 这正是 macvlan（`mode bridge`，挂在物理 WAN 口上）的作用 |

### 4.2 实现方式

- 第 2 条会话起，用 **macvlan** 在物理 WAN 设备上创建独立 MAC 的下层设备
  （接口名用短名 `crwanN`，因为 Linux 接口名上限 15 字符），每条会话一个独立 MAC + 独立 `pppname`；
- 会话由 netifd 管理（普通 `wanN` 段），由本项目的守护进程串行冷启动拨号（拨一条、等它稳、再拨下一条）；
- **池大小由账号决定**：所有启用账号的 `max_connections` 之和 = `pool_size`；
- **认证间隔用 60 秒**：实测 5 秒间隔只能收敛 2/5 条，60 秒可收敛 5/5。

### 4.3 分流：mwan3

把池里的会话注册进 mwan3（`wan`/`wan2`/… 各作一个 member），并用一条**本项目自己的**策略规则
（按连接加权分摊）抢在出厂规则之前生效。

一个实测踩到的坑：mwan3 给每个接口建"每接口路由表"时，数据源是 `ip route list table main`；
而 **netifd 只会给"主"PPPoE 装默认路由**，`wan2/wan3` 的默认路由从来没进 main 表，
于是 mwan3 判这些接口 `error (16)` 并把它们排除出策略——**看起来在池里，实际所有流量回落到一条会话**。
修法是让每条会话的默认路由直接进它自己的路由表（`network.wanN.ip4table`），或给它 `defaultroute 1`。
详见 [05-故障排查.md](05-故障排查.md)。

## 5. 带宽：为什么能叠加、能叠多少

- 单条会话的持续下行有限（实测 **40~100 Mbps**，有突发）；
- 多条会话同时打流，总吞吐**近似线性**（实测三条会话 41 → 117/119 Mbps，接近 3×）；
- 因此 5 条会话的聚合在实测中出现过 **~500 Mbps** 量级；但具体数字高度依赖时段、
  测速端点与客户端能力。

> ⚠️ **测量方法本身是个大坑**：如果让路由器自己跑 TLS 去测（例如在路由器上 `curl` 12 路 HTTPS），
> 瓶颈会先落在**路由器的 CPU**上（实测只有 ~79 Mbps），根本测不到链路或代理的上限。
> 正确做法是让**别的机器**做 TLS，路由器只转发。详见 [05-故障排查.md](05-故障排查.md) 的"测量方法学"。

## 6. SNI 分流：对抗按域名的限速

### 6.1 被对抗的是什么

链路中间的 DPI 设备会解析 TLS ClientHello，读出其中的 **SNI（域名）**，对黑名单里的域名限速。
注意它限的是**域名**，不是 IP——所以同一个 IP 上的不同域名待遇可以不同。

### 6.2 对抗思路

让 DPI **读不到或读错** SNI，使这条连接落回默认（不限速）类别。工程上常用的几种手法：

| 手法 | 做法 |
| --- | --- |
| **split / multisplit** | 把 ClientHello 拆成多个 TCP 段发送，让只按单包解析的 DPI 看不到完整 SNI |
| **disorder** | 打乱分段的发送顺序，DPI 需要重组才能读到 SNI |
| **fake** | 先发一个"假的" ClientHello（伪造的 SNI / 非法校验），让 DPI 记住错误的域名，真正的握手随后进行 |

本项目用上游工具 **zapret** 实现（`nfqws` 或 `tpws` 两种模式），配置里对 80/443 分别指定策略。
这些手法只作用于**握手的头几个包**，不碰后续数据——这正是 `nfqws` 高效的原因。

### 6.3 两种模式的关键差别（本项目实测）

| | **nfqws** | **tpws** |
| --- | --- | --- |
| 实现位置 | 内核 NFQUEUE（`connbytes` 限制只把**每连接前几个包**送进用户态） | 用户态**透明代理**（`nat` 跳转到 `127.0.0.127:988`） |
| 数据面 | 载荷完全留在内核快路径 | **两个方向**的载荷都要过一遍用户态进程 |
| 需要内核支持 | 需要 NFQUEUE（`xt_NFQUEUE` + `nfnetlink_queue`） | 只需要 `nat` 表，几乎所有固件都有 |
| 本项目实测（转发路径，16 路明文 HTTP） | **312.5 / 314.7 Mbps** | **173.1 / 180.4 Mbps** |
| 对照：完全不经手 | 355.1 Mbps | — |

值得特别说明的一点：**"上行不受影响"不代表下行没被处理**。tpws 是代理，两个方向都要过用户态；
上行看起来无损，只是因为**上行线速率（250 Mbps）低于 tpws 的处理天花板**，而下行高于它。
（早期文档里"上行是内核直通、只有首包走 tpws"的说法是错的，已在
[reference/SNI-DESYNC.md](reference/SNI-DESYNC.md) 与工作日志中更正。）

### 6.4 hostlist 的语义（反直觉，必须记住）

- `--hostlist=<文件>` 表示"**只处理名单里的域名**"；
- 但**文件存在却是空的**（0 字节）在实测中等于"**匹配所有主机**"（v72.13，debug 日志里
  profile 标注 `(empty)`，且不做任何 hostlist 检查就直接命中）。
- 所以：**"名单是空的" ≠ "分流没生效"**，而是"对全部域名做 desync"。本机就是故意留空的用法。
- 反过来，想让"大流量站点不限速地跑"而只保护少数域名，应该用**排除集**（`nozapret`，
  DNAT 规则本来就用 `-m set ! --match-set nozapret dst`）或改成"只让名单目标进代理"的白名单模式。

## 7. 为什么路由器上还需要"自编内核模块"

通用 OpenWrt 设备只要内核带 NFQUEUE 就能直接用 nfqws。但本项目实测的这台 Redmi AX3000
用的是**社区自编的 QSDK 供应商内核**：

- 官方 OpenWrt 从来没有 ipq50xx 这个 target，core feed 404，**装不上任何 target 级 kmod**；
- 借用别的 target 的同架构 kmod 也不行（`vermagic` 与 PLT 段不匹配）；
- 更狠的是：**`vermagic` 相同也不代表 ABI 相同**——QSDK 改过 `struct net_device`（本例大 64 字节），
  用上游头文件编出来的模块 `insmod` 会成功，但一碰结构体就 panic。

所以要么放弃这些内核模块，要么**用厂商自己的内核源码树 + 设备原装 config 自己编**。
本项目走的是后者，并配了一套**离线 ABI 闸门**（配置保真比对、编译期 `offsetof` 表、
符号对照）来保证"能编出来"真的等于"能装上去不炸"。

具体做法、踩过的坑与验收记录见 [03-部署-AX3000-自编内核模块.md](03-部署-AX3000-自编内核模块.md)，
深度技术细节见 [reference/AX3000-KMOD-BUILD.md](reference/AX3000-KMOD-BUILD.md)。

## 9. 设计边界（本项目**不**做的事）

- 不绕过认证、不伪造凭据、不修改白名单、不探寻未授权带宽通道；
- 只恢复/维护**用户自己已有**的拨号连接，只操作配置中指定的 WAN 接口与本包自己创建的派生接口；
- 凭据只写入设备上的 UCI 配置文件（权限 `0600`），**不会**出现在状态 RPC、日志或前端返回值里；
- 探针与测速端点默认值是示例，正式部署请替换为自己或学校明确授权的健康检查地址。
