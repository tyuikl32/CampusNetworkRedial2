# 部署（本机）：Redmi AX3000 的特殊改动与自编内核模块

> 本文只讲**这台实测机型**上额外要做的事。通用部署流程（构建/安装 LuCI 应用、初始化配置）见
> [02-部署-通用.md](02-部署-通用.md)。原理见 [01-项目原理.md](01-项目原理.md)。

## 0. 一句话结论

这台 Redmi AX3000 跑的是**社区自编的 QSDK 供应商内核**，官方 OpenWrt 从来没有支持过它的 target，
所以 `opkg` **装不上任何 target 级内核模块**；而多拨（macvlan）、mwan3 加权分流（xt_statistic）、
以及 SNI 分流的首选模式（NFQUEUE）**都依赖内核模块**。

解决办法：**用厂商自己的内核源码树 + 设备原装内核配置，自己编**，并用一套离线 ABI 闸门保证
"编得出来"确实等于"装上去不会崩"。本项目在这台机器上先后自编并装上了四个模块，全部稳定运行、
`tainted` 保持 0、重启后可自动加载。

## 2. ⚠️ 最难的一条：`vermagic` 相同 ≠ ABI 相同

这条是本项目踩过最深的坑，**不要再走一遍**：

- 用设备的 `/proc/config.gz` 当 `.config`，在上游 `linux-5.4.164` 上编 `macvlan.ko`：
  - `vermagic` **完全一致**、`.plt` 段存在、没开 `CONFIG_MODVERSIONS`、没开模块签名 ⇒ `insmod` **成功**；
  - 一旦用这个模块去建接口，**内核立刻 panic**。
- 根因：设备内核是**厂商 QSDK 树**（`linux-ipq-5.4` @ `d5fcb18e`），它改过 `struct net_device`：
  `CONFIG_WIRELESS_EXT`（+8）、`priv_flags_ext`（+4）、`local_addr_mask[32]`（+32）、
  以及 `_tx` 的 64 字节对齐填充（+20）——**合计 +64 字节**。用上游头文件里的偏移去碰结构体必炸。
- ⇒ **结论：必须同时满足"厂商源码树"+"设备原装配置"两个条件**，只满足后者会 panic。

## 3. 自编流水线

### 3.1 材料

| 材料 | 从哪来 | 落地位置 |
| --- | --- | --- |
| **QSDK 内核源码** `linux-ipq-5.4` @ `d5fcb18e5420670c8734c6a659873e73adab6dac` | 主源 `https://git.codelinaro.org/clo/qsdk/oss/kernel/linux-ipq-5.4`（约 167 MB）；国内可用 GitHub 镜像 `CodeLinaro-mirror/qsdk_oss_kernel_linux-ipq-5.4` + `https://ghfast.top/` 前缀 | 解包到 **WSL 内 ext4**：`/opt/kmod-build/linux-ipq-5.4` |

| ARMv7 交叉工具链 | Bootlin `armv7-eabihf--glibc--stable-2022.08-1`（gcc 11.3） | WSL：`/opt/kmod-build/armv7-eabihf--glibc--stable-2022.08-1` |

### 3.2 大件放哪：`CR_KMOD_CACHE`

约 1.9 GB 的源码归档、解包后的内核源码树、工具链**不入库**，放在仓库外的缓存目录：

```
D:\CampusNetworkRedial\kmod-build-cache\        # 默认位置，可用环境变量 CR_KMOD_CACHE 覆盖
├── qsdk/linux-ipq-5.4-<sha>.tar.gz             # QSDK 源码归档
├── linux-5.4.164.tar.xz                        # 上游内核源码（早期走过弯路的对照）
├── linux-5.4.164/                              # 上游内核源码树
└── armv7-toolchain.tar.bz2                     # 工具链归档
```

`wsl-setup.sh` 与 `wsl-extract-qsdk.sh` 里的 `CACHE=` 就指向它。

### 3.3 脚本清单（都在 `CampusRedialWrt/kmod-build/`）

| 脚本 | 作用 |
| --- | --- |
| `wsl-setup.sh` | 在 WSL 内解包内核源码与工具链到 `/opt/kmod-build`（ext4），并放入设备内核配置 |
| `wsl-extract-qsdk.sh` | 解包 QSDK 源码到 `/opt/kmod-build/linux-ipq-5.4` 并校验**源码身份**（`EXTRAVERSION` 为空、`priv_flags_ext`/`local_addr_mask` 存在、`WIRELESS_EXT` 有 prompt） |
| `wsl-qsdk-build.sh` | **主构建**：播种设备配置 → `olddefconfig` + `modules_prepare` → 配置保真闸门 → 编 `macvlan.ko` / `tun.ko` / `xt_statistic.ko` → ABI 自查 |
| `wsl-nfqueue-build.sh` | 同上，编 **NFQUEUE 两件套**（`nfnetlink_queue.ko` + `xt_NFQUEUE.ko`），并做回归（重编 `tun.ko` 验证构建环境没漂） |

| `wsl-offdump.sh` + `offdump/cr_offdump.c` | **只编译、永不加载**的 `offsetof` 探针：把每个字段写成 `char cr_<f>[offsetof(...)]`，数组长度即偏移，用 `readelf -s` 读出 |
| `wsl-final.sh` / `abi-compare.sh` / `offset-hist.py` / `missing-syms.sh` / `static-check.sh` | 辅助判据（跨编译器时噪音大，只作参考） |
| `pkg/mkunipk.py` | 生成 OpenWrt 21.02 格式的 `.ipk`（`gzip(tar(debian-binary, control.tar.gz, data.tar.gz))`，外层 gzip 必需） |
| `pkg/mk-nfqueue-pkgs.py` | 打 NFQUEUE 那两个自编包（见 §4.2） |
| `remote/cr-*.sh` | **上机脚本**（从 PC 推送到设备 `/tmp` 执行）：加载/建接口验证、持久化、连接池探针、带宽诊断、SNI 模式切换、转发路径测试客户端等 |

## 4. 这台机器上编了哪些模块、为什么

| 模块 | 为什么需要 | 上游包名 | 状态 |
| --- | --- | --- | --- |
| `macvlan.ko` | 多拨必需：每条 PPPoE 会话要**独立源 MAC**（BRAS 禁止同 MAC 多会话） | `kmod-macvlan` | 已持久化，池子 4~5 路会话正常 |
| `xt_statistic.ko` | mwan3 的加权按连接分流要用 `-m statistic` | `kmod-ipt-ipopt` | 已持久化，mwan3 正常 |
| `nfnetlink_queue.ko` | **NFQUEUE 的队列处理器**（zapret `nfqws` 模式的必需品） | `kmod-nfnetlink-queue` | 已持久化，随 nfqws 运行 |
| `xt_NFQUEUE.ko` | iptables 的 `NFQUEUE` target | `kmod-ipt-nfqueue` | 已持久化 |

### 4.1 ABI 闸门（三道，缺一不可）

1. **`vermagic` 必须逐字符等于** `5.4.164 SMP preempt mod_unload ARMv7 p2v8`
   （注意 modinfo 字符串**带尾空格**，比较前先裁剪）；`license=GPL`。
2. **配置保真**：把设备 config 与本地 `olddefconfig` 后的 `.config` 逐行 diff，差异必须**逐条可解释**
   （编译器身份 2 行、因为目标符号可见而新出现的隐藏项、`YT9215_PHY` 这类设备独有补丁、
   以及我们**有意**提升为 `=m` 的那几个模块）。
   另外单独核对**决定结构体布局的符号**：`WIRELESS_EXT`、`SKB_RECYCLER`、`NET_CLS_ACT`、
   `MODVERSIONS`、`MODULE_SIG`、`ARM_MODULE_PLTS`、`PREEMPT`、`SMP` 等，**逐项一致**。
3. **符号可解析**：
   - 函数符号：本模块的未定义符号必须能在设备 `/proc/kallsyms` 里找到；
     ⚠️ 设备**没开 `KALLSYMS_ALL`**，kallsyms **只有函数、没有数据符号**——
     `nf_ct_hook` / `kmalloc_caches` / `jiffies` 这类"查不到"是正常的，不能当失败。
   - 数据符号：改用**厂商树里的 `EXPORT_SYMBOL` + 提供它的 `CONFIG_*` 在设备上确实已构建**来证明
     （例：`nf_ct_hook`/`nfnl_ct_hook` 由 `net/netfilter/core.c` 导出，`nfnetlink_*` 由
     `nfnetlink.c` 导出且设备 `CONFIG_NETFILTER_NETLINK=m` 已加载）。
4. **回归锚点**：每次构建都顺手重编一个"参照模块"（`tun.ko`），确认它的
   `netdev_priv` 常量仍是 `0x580`（= `ALIGN(sizeof(struct net_device),32)` = 1408）。
   这个值一旦变化，说明构建环境/源码树漂了，**立刻停下**。

> 上机前的最后一道闸门永远是**真机 `insmod`**：符号缺失会以 `Unknown symbol` **干净失败**，
> 不会崩内核。真正危险的是 ABI 不匹配（能装上、一用就崩），所以才需要上面这些离线判据。

### 4.2 打包：按上游包名拆成两个

`iptables-mod-nfqueue`（用户态）的依赖是
`libc, iptables, kmod-nfnetlink-queue, kmod-ipt-nfqueue`，所以**内核侧必须拆成这两个名字**，
opkg 才能自己把依赖解析掉（否则会撞上那句极具误导性的
`... found, but incompatible with the architectures configured`）。

| 包名 | 内容 |
| --- | --- |
| `kmod-nfnetlink-queue` | `/lib/modules/5.4.164/nfnetlink_queue.ko` + `/etc/modules.d/nfnetlink-queue` |
| `kmod-ipt-nfqueue` | `/lib/modules/5.4.164/xt_NFQUEUE.ko` + `/etc/modules.d/ipt-nfqueue` |
| `kmod-ipt-ipopt` | `xt_statistic.ko`（同上套路，mwan3 用） |

**用户态**部分不要自己编，从**其它 target 的 core feed 取同架构包**即可
（本例：`ipq40xx/generic` 的 21.02.7 core feed，架构同样是 `arm_cortex-a7_neon-vfpv4`）：

```sh
# 在 PC 上下载后传到设备
curl -O https://downloads.openwrt.org/releases/21.02.7/targets/ipq40xx/generic/packages/iptables-mod-nfqueue_1.8.7-1_arm_cortex-a7_neon-vfpv4.ipk
# 校验 sha256 与 feed 索引（Packages.gz）里的一致，再安装
```

### 4.3 安装顺序与开机加载

```sh
# 依赖在前，用户态在后；不要用 --force-depends
opkg install /tmp/kmod-nfnetlink-queue.ipk
opkg install /tmp/kmod-ipt-nfqueue.ipk
opkg install /tmp/iptables-mod-nfqueue.ipk

# 内核模块持久化（等价于包安装后的结果）
#   /lib/modules/5.4.164/{nfnetlink_queue.ko,xt_NFQUEUE.ko}
#   /etc/modules.d/{nfnetlink-queue,ipt-nfqueue}
```

`/etc/modules.d/` 里的文件名决定开机加载顺序（kmodloader 按文件名排序，数字 < 字母）：
`nf-*` → `nfnetlink` → **`nfnetlink-queue`** / **`ipt-nfqueue`**，两个新文件都排在依赖之后，方向正确。
**已实测重启验证**（见 §6）。

## 5. SNI 分流在这台机器上的落地

### 5.1 为什么最终选了 nfqws

出厂内核没有 NFQUEUE，所以最早只能用 **tpws**（用户态透明代理）。代价很实在：
**两个方向的载荷都要过用户态**，实测转发路径上 16 路明文 HTTP 只有 **173~180 Mbps**，
而完全不经手的对照是 **355 Mbps**。

自编出 NFQUEUE 两件套后切到 **nfqws**，同一负载 **312~315 Mbps**——**回到"不经手"的量级**，
而每连接只有**前 3 个包**进用户态（16 条连接整轮共 48 个包）。

### 5.2 落地的规则形状

```
mangle POSTROUTING（出向，每个 WAN 设备各一条 tcp 80,443 + 一条 udp 443）
  -o pppoe-wanN -p tcp -m mark ! --mark 0x40000000/0x40000000 \
     -m multiport --dports 80,443 \
     -m connbytes --connbytes 1:6 --connbytes-mode packets --connbytes-dir original \
     -m set ! --match-set nozapret dst -j NFQUEUE --queue-num 200 --queue-bypass

mangle FORWARD / INPUT（入向，每设备各一条）
  -i pppoe-wanN -p tcp -m multiport --sports 80,443 \
     -m connbytes --connbytes 1:3 --connbytes-mode packets --connbytes-dir reply \
     -m set ! --match-set nozapret src -j NFQUEUE --queue-num 200 --queue-bypass
```

要点：`connbytes` 把处理限制在每连接头几个包；`--queue-bypass` 保证 **nfqws 万一挂掉时流量自动放行**
（不会变成黑洞）；`mark` 位用于防止 nfqws 自己发出的包被再次排队。

### 5.3 切换与回滚脚本

```sh
sh /tmp/cr-nfq-switch.sh status    # 看当前模式/跳转/NFQUEUE 规则数/连通性
sh /tmp/cr-nfq-switch.sh on        # tpws -> nfqws
sh /tmp/cr-nfq-switch.sh off       # nfqws -> tpws（用 /opt/zapret/config.tpws.bak 还原）
```

脚本里包含两个**必须**的安全动作：

1. 停用 tpws 前先 `touch /var/run/zapret.off` 并**先摘跳转再停进程**——否则会留下指向死端口的
   `nat` 跳转，导致整个 LAN 的 80/443 全部 connection refused（连 LuCI 面板也打不开）；
2. 摘完跳转后**无条件补扫**所有 `--to-destination 127.0.0.127:988` 规则。
   原因：zapret 只枚举"当前存在"的 WAN 设备，**切换那一刻 down 掉的会话，它那条 OUTPUT 规则摘不掉**，
   等会话重新上线就会把路由器本机经该会话的 80/443 打进死端口（本机实测抓到过一条 `pppoe-wan5` 的残留）。

### 5.4 hostlist 的用法

本机 `zapret-hosts-user.txt` **故意留空**：实测（v72.13）**空名单 = 匹配所有主机**，
也就是"对所有域名都做 desync"。面板上的"名单域名数"显示 0 并不代表没生效。
想只保护少数域名，就填名单；想让大流量站点不受影响，用 `nozapret` 排除集或改成白名单模式
（见 [01-项目原理.md](01-项目原理.md) §6.4）。

## 6. 验收记录（本机实测）

| 项目 | 结果 |
| --- | --- |
| ABI 闸门 | vermagic/license 全部一致；配置差异 15 行全部可解释；结构体 CONFIG 门逐项一致；未定义符号（函数 61/66、9/10 命中 kallsyms，其余为数据符号且有 `EXPORT_SYMBOL` 佐证） |
| 上机 `insmod` | `nfnetlink_queue` / `xt_NFQUEUE` rc=0；`/proc/net/ip_tables_targets` 出现 `NFQUEUE`；`tainted=0`；`dmesg` 无 oops；网络与拨号不受影响 |
| 规则落地 | mangle 共 **16 条** NFQUEUE 规则（4 条会话 × 出向 tcp/udp + 入向 FORWARD/INPUT） |
| 每连接开销 | 16 条连接一轮测速只让 NFQUEUE 计数涨 **48**（每连接 3 个包） |
| **desync 实证** | 临时 debug 实例（独立队列号，只对单个目标）：`packet contains full TLS ClientHello` → `hostname: mirrors.aliyun.com` → `multisplit pos: 1 323` → 注入 fake → 原包 `drop`，而连接仍然 `http=200` 下载完成；后续包带 `mark=40000700` 被 `pass unmodified`（防自环有效） |
| **带宽 A/B**（转发路径 16 路明文 HTTP，8 s 窗口） | tpws **173.1 / 180.4** Mbps；nfqws **312.5 / 314.7** Mbps；完全不经手对照 **355.1** Mbps |
| 重启验证 | 50 秒恢复；模块**开机自动加载**（`nfnetlink_queue` 引用数 1 = nfqws 持有）；4 路池子全部恢复；NFQUEUE 规则随各路 `ifup` 自动补齐到 16 条 |
| 健康 | `tainted=0`、无 oops、`uptime` 未归零、外网与面板均 200 |

**规则为什么能自动补齐**：靠 fw3 自带的 `/etc/hotplug.d/iface/20-firewall`，每次接口 `ifup` 都会重载
防火墙、从而重跑已注册的 include（`uci show firewall` → `@include[].path='/etc/firewall.zapret'`,
`reload=1`）→ `zapret_apply_firewall` → 给"当前存在的所有 WAN"装规则。
⇒ zapret 自带的 `/etc/hotplug.d/iface/90-zapret` 在本机**并不存在，也不需要**。

| --- | --- |
| `network` | 每个池会话：`campus_wanN_device`（`type=macvlan`、`ifname=eth0`、`mode=bridge`、独立 `macaddr`）+ `wanN`（`proto=pppoe`、独立 `pppname`、`ipv6=0`、`delegate=0`、`auto=0`、`campus_redial_managed=1`） |
| `mwan3` | 追加 `wan2/wan3/…` + `cr_wan*_member` + `cr_balanced` + `cr_default_ipv4`，并把本项目的规则**置顶**以抢在出厂规则之前 |
| `firewall` | `wan2/wan3/…` 归入 wan zone |
| `/opt/zapret/config` | SNI 分流配置（模式、策略、`OPENWRT_WAN4`、`MODE_FILTER`）；tpws 备份在 `/opt/zapret/config.tpws.bak` |

回滚：

```sh
# 只回滚连接池
uci -q delete network.campus_wan2_device; uci -q delete network.wan2; uci commit network
uci -q delete mwan3.cr_balanced; uci -q delete mwan3.cr_default_ipv4; uci commit mwan3
# 回滚 SNI 分流（回到 tpws）
sh /tmp/cr-nfq-switch.sh off
# 连内核模块一起卸
opkg remove iptables-mod-nfqueue kmod-ipt-nfqueue kmod-nfnetlink-queue
rmmod xt_NFQUEUE nfnetlink_queue        # 或者直接重启（开机不会再加载）
```

> 变更纪律：装/删内核模块、改 `/etc/config/network`、跑会打断 WAN 的拨号实验、重启，
> 都属于"严肃更改"，应当先说明并取得机主同意再执行。
